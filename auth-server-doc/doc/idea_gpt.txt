# OIDC 導入方案：從簡單到複雜

建議採取由簡到難、逐步提升安全性與自動化程度的方式導入 OIDC，同時確保既有帳號的相容性。

核心原則是：不要一開始就把所有產品、登入、登出和身分管理一次做完。先建立穩定的使用者識別碼，再逐步導入 OIDC，最後才處理跨產品的進階功能。

## 1. 方案總覽

### 方案 A：最小可行實作（MVP）

**最推薦的起點**

先建立 UUID、最小 OIDC Provider，並讓一個產品完成端到端登入。

複雜度：低至中｜適合驗證架構與核心風險

### 方案 B：分階段遷移

先完成共用基礎設施，再由各產品獨立驗收、切換及退場。

複雜度：中｜適合正式上線與多產品協作

### 方案 C：完整生產級安全架構

加強 KMS、金鑰輪替、併發控制、監控、稽核及回復演練。

複雜度：中至高｜正式環境的必要能力

### 方案 D：完整跨產品身分與登出管理

進一步處理跨產品登出、Session 同步、帳號切換與進階身分管理。

複雜度：高｜建議另立專案

**重要區分：** 方案 A–C 是完成目前 OIDC 議題的不同實作策略與成熟度；方案 D 則包含目前議題明確排除的功能，不應為了完成 OIDC 而一起納入。

## 2. 方案 A — 最小可行實作（先跑通一個產品）

**想法：** 先證明 OIDC 登入可以正常運作，再擴大到其他產品。

### 實作步驟

**Step 1 — 建立 Canonical User UUID**

- 為既有帳號回填 UUID。
- 確認會員對應與唯一性。

**Step 2 — 建立最小 OIDC Provider**

實作 Discovery、Authorization、Token、UserInfo、JWKS 等必要端點。

**Step 3 — 選一個 RP 做整合**

驗證登入、既有會員對應、新會員處理及 rollback。

**Step 4 — 完成安全驗收**

測試通過後，再決定如何推進其他產品。

### 實作方式

1. 直接在現有後端建立獨立的 OIDC Provider module，不必先拆成獨立微服務。
2. 使用資料庫保存 Authorization Code 與短效 Access Token，確保兌換操作具備原子性。
3. 先採用靜態 Client Registration，由管理者設定 Client ID、Redirect URI 與 Secret。
4. 使用標準 OIDC library 處理協議細節；自訂部分集中在使用者查詢、Token 簽發及會員對應。
5. 選擇一個 RP，建立完整的測試流程，包括舊會員、新會員、重複會員、登入失敗及回復 Legacy SSO。

### 優缺點

- **優點：** 改動範圍小、容易除錯，可以早點驗證關鍵假設。
- **缺點：** 第一個產品的成功不代表正式環境的 KMS、金鑰輪替和所有安全情境都已解決。
- **風險：** 如果把 MVP 直接當成 production-ready，可能忽略高風險的身分驗證與資料一致性問題。

**適用情境：** 團隊還不確定 OIDC 的整合方式，或希望先降低技術不確定性。

**注意：** 這個方案可以縮小初期實作範圍，但不能省略正式上線前必要的安全驗收。

## 3. 方案 B — 依照 Phase 0–5 分階段實作（最推薦）

這是最推薦的正式執行策略，因為它能將共用基礎設施、產品驗收條件及回復機制清楚分開。

| 階段      | 主要工作                                   | 交付成果         |
| ------- | -------------------------------------- | ------------ |
| Phase 0 | UUID、資料回填、會員 mapping、Legacy regression | 身分資料穩定       |
| Phase 1 | OIDC endpoints、Token store、協議測試        | 非正式環境端到端登入   |
| Phase 2 | KMS、JWKS rotation、監控、Conformance Tests | 正式環境上線準備完成   |
| Phase 3 | 每個 RP 的 staging 整合及 rollback drill     | 單一產品驗收通過     |
| Phase 4 | 單一 RP atomic cutover                   | 該產品正式使用 OIDC |
| Phase 5 | 移除該 RP 的 Legacy login path             | 該產品完成遷移      |

### 關鍵設計：共用基礎設施，各產品獨立遷移

```
                   ┌──────────────────┐
                   │  OIDC Provider   │
                   └────────┬─────────┘
                            │
             ┌──────────────┼──────────────┐
             │              │              │
          ┌──▼────┐     ┌───▼─────┐    ┌───▼──────┐
          │Product A│   │Product B│    │Product C │
          └────────┘    └─────────┘    └──────────┘
             │              │              │
          獨立驗收         獨立驗收         獨立驗收
          獨立切換         獨立切換         獨立切換
```

### 如何降低實作成本

- **不要重複造輪子：** 使用成熟的 OIDC library，優先重用標準協議實作。
- **先做共用測試工具：** 建立可重複使用的 RP integration test suite，避免每個產品各自發明驗收方式。
- **把會員 mapping 獨立測試：** 將 `sub → UserData.uuid → RP.user_uuid` 的身分對應與登入流程分開驗證。
- **把 rollback 當成交付的一部分：** 不能只測試 OIDC 成功登入，也要驗證回復 Legacy 後仍然是同一個會員。
- **以產品為單位切換：** 一個產品發生問題，不應迫使其他產品一起回復。

這個方案不一定是程式碼最少的方案，但通常是多產品正式遷移時，風險與維護成本最平衡的方案。

## 4. 方案 C — 生產級安全架構（在方案 B 上加強）

**想法：** 不只讓登入成功，而是確保登入在併發、故障、金鑰輪替與攻擊情境下仍然安全。

這不是另一套不同的登入流程，而是在方案 B 的基礎上，增加必要的 production engineering。

### 建議的技術設計

#### 1. 金鑰管理與輪替

- 透過 Cloud KMS 簽署 ID Token。
- 透過 JWKS 公開驗證用的公鑰。
- 新舊金鑰重疊發布，避免輪替期間登入失敗。
- 遇到未知 `kid` 時重新取得 JWKS；驗證失敗一律拒絕，不可降級放行。

#### 2. Token 與併發控制

- Authorization Code 使用一次性兌換機制。
- 透過資料庫交易或條件式更新，確保同一個 Code 不能被兩個請求同時兌換。
- 對過期、重複使用及不符合 Client、Redirect URI 或 PKCE 的請求一律拒絕。

#### 3. 監控與事故處理

- 監控登入成功率、Token 兌換失敗率及 KMS 錯誤。
- 針對身分衝突、簽章錯誤與異常登入失敗設定告警。
- 明確定義事故負責人、回復條件及操作手冊。

#### 4. 自動化安全測試

- 建立協議測試、負向測試及併發測試。
- 執行 OpenID Foundation Conformance Tests。
- 在 staging 演練金鑰輪替、儲存故障與 rollback。

### 如何避免過度工程化？

不需要第一天就建立複雜的管理介面、金鑰輪替排程器或通用身分管理系統。

建議先做：

1. 可測試的 signer interface。
2. 正式環境使用 Cloud KMS。
3. 最小但可靠的 metrics、alerts 與 runbook。
4. 針對核心風險設計自動化測試。
5. 等實際需求出現後，再增加自動化管理能力。

**我的判斷：** 對身分驗證系統而言，安全性不是可有可無的進階功能。方案 C 中與正式環境相關的部分，應視為正式上線的必要條件，而不是等所有產品遷移完才處理。

## 5. 方案 D — 完整跨產品身分與登出管理

這是複雜度最高的方向，適合當成後續獨立專案。

目前的 OIDC 議題主要解決「如何以標準協議登入並辨識正確的會員」，不會自動解決所有產品的 Session 管理。

### 可以進一步處理的能力

| 功能                  | 解決的問題                      | 複雜度 |
| ------------------- | -------------------------- | --- |
| RP-Initiated Logout | 從產品發起共用登入 Session 的登出流程    | 中   |
| Back-Channel Logout | 由身分服務通知其他產品，使對應 Session 失效 | 高   |
| Session ID 對應       | 確認哪些產品 Session 屬於同一次登入     | 高   |
| Token 撤銷與失效         | 確保已登出的 Session 或憑證不能繼續使用   | 高   |
| 帳號切換                | 讓使用者明確切換至另一個帳號             | 中至高 |
| 跨裝置登出               | 控制其他裝置上的登入 Session         | 高   |

### 為什麼複雜？

例如，使用者同時登入 Product A、Product B 和 Product C，並從 Product A 選擇「登出所有產品」。

系統不能只刪除 Product A 的 Cookie，或只清除共用登入服務的 Cookie。還需要：

1. 確認本次登入對應哪些產品 Session。
2. 由身分服務通知相關產品。
3. 各產品在伺服器端驗證通知，並使對應 Session 失效。
4. 處理通知失敗、重送及重複事件。
5. 確保不會意外登出其他裝置或不相關的 Session。

另外，若產品使用自有 JWT，單純刪除 Cookie 並不能讓已被複製的 Token 自動失效。

因此，建議先完成標準 OIDC 登入，再另外定義跨產品登出合約及驗收標準，避免擴大目前議題的範圍。

## 6. 四種方案比較

| 比較項目           | A：MVP  | B：分階段遷移 | C：生產級安全 | D：跨產品管理       |
| -------------- | ------ | ------- | ------- | ------------- |
| 主要目標           | 驗證可行性  | 完成產品遷移  | 確保生產可靠性 | 完整 Session 管理 |
| 初期開發成本         | 低      | 中       | 中至高     | 高             |
| 上線安全性          | 尚需補足   | 取決於安全驗收 | 完整度最高   | 需另外設計         |
| 適合時機           | 初期 POC | 正式開發    | 正式上線前   | 後續擴充          |
| 是否屬於目前 OIDC 範圍 | 部分     | 是       | 是       | 主要屬於後續工作      |

## 7. 我會如何實際執行

我的建議不是從四種方案中只能選一種，而是將它們組合成一條實際可執行的路線。

### 1. 先處理 Phase 0

先確保 UUID、會員 mapping、資料回填與 Legacy regression 都正確。這是後續所有工作共同依賴的基礎。

### 2. 用方案 A 驗證最小完整流程

建立 OIDC Provider，選一個 RP 完成端到端登入。先驗證架構，不要一次改動所有產品。

### 3. 依方案 B 完成共用基礎設施與逐產品遷移

Phase 1、Phase 2 依序通過驗收，再讓各 RP 分別完成 Phase 3–5。

### 4. 將方案 C 的安全條件設為上線 Gate

不論採用哪種開發策略，正式環境都必須具備必要的金鑰管理、測試、監控及回復機制。

### 5. 最後才評估方案 D

將跨產品登出、Session 撤銷及帳號切換獨立規劃，避免擴大目前議題的範圍。

### 實作時最值得優先釐清的三件事

1. **先確認既有程式碼能否重用。** 評估現有後端、Token 儲存機制、會員資料結構與 Legacy SSO 的實作，避免重複建設。
2. **先定義身分對應的不變條件。** `sub` 必須穩定對應 `UserData.uuid`，RP 必須能將它對應到正確的既有會員，且衝突時不可自動猜測或合併。
3. **先定義每個 Phase 的驗收證據。** 測試通過、KMS 演練結果、Conformance 測試與 rollback 記錄都應可查驗，而不是只以程式碼已合併判定完成。

總結來說，我會選擇 **「A 驗證、B 推進、C 把關、D 後續擴充」**。這樣可以控制初期投入，同時保留完成正式環境安全驗收所需的工程品質。
